## Build it locally
Needs: Node 22, Java 17 or newer, and the Android SDK (platform 37, build-tools 37.0.0, NDK 27.1.12297006, CMake 3.22.1).

```bash
cd app
npm ci
npx expo prebuild --platform android --no-install   # generates app/android (not committed)
cd android
ANDROID_HOME=/path/to/android-sdk NODE_ENV=production ./gradlew assembleRelease
# result: app/android/app/build/outputs/apk/release/app-release.apk
```
First build: about 10 minutes. Later builds: about 6.

**If dependency downloads fail with "429 Too Many Requests" or "Could not find …"** — Maven Central rate-limits busy addresses. In the cloud session this was solved by a machine-local Gradle file (`~/.gradle/init.d/central-mirror.gradle`, not in the repository) that tries Google's official Maven Central mirror first: `https://maven-central.storage-download.googleapis.com/maven2/`. A home or office connection normally does not need it.

The project configuration is compatible. It needs an Expo account owned by the project, which does not exist yet, and `npx eas-cli build -p android --profile preview`. Nothing is set up for this; it is the fallback if local builds become a burden.

## Signing — read before giving the APK to anyone
- The current APK is signed with the Android **debug** key. Anyone can produce that key, so it proves nothing about who built the file, and an app signed with it cannot later be updated by an app signed with a real key (the user would have to uninstall first).
- Before the APK goes to officials, create a real signing key **once**, on the founder's machine:
  ```bash
  keytool -genkeypair -v -keystore cop32-guide-release.jks -alias cop32guide -keyalg RSA -keysize 4096 -validity 10000
  ```
  Keep the `.jks` file and its passwords in a password manager and one offline backup. **Never commit it** (`*.jks` and `*.key` are already ignored in `app/.gitignore`) and never paste the passwords into a chat or a file in the repository. If the key is lost, the app can never be updated in place.
- Point the release build at it through Gradle properties kept outside the repository (`~/.gradle/gradle.properties`), not through edits to committed files. The exact wiring will be added to this runbook when the first real key exists.
- Who holds the key is an ownership question (D35, D72): whoever holds it controls every future update.

## Check a built APK
```bash
B=$ANDROID_HOME/build-tools/37.0.0
ls -la app-release.apk                                   # size
$B/aapt2 dump badging app-release.apk | grep -E "package|SdkVersion|uses-permission|application-label"
$B/apksigner verify --print-certs app-release.apk        # who signed it
```
Expect: label `COP32`, `minSdkVersion:'24'`, from version 1.0.0 a single `uses-permission` line for `ACCESS_NETWORK_STATE` and **no `INTERNET` line** (D80; up to 0.9.0 both were present) (plus an internal one ending `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`, which is not a user permission).

## Signing for a store release (not done)
Every APK so far is signed with a throwaway test key, which is right for sideloading and wrong for a store. A store release needs a signing key that the founder creates and keeps — never in this repository and never in a cloud session. Losing that key means the app can never be updated under the same listing. Steps, when the time comes: create an upload keystore on the founder's own machine; store it and its passwords in a password manager with a second copy offline; configure it through Gradle properties or Expo's build service; enrol in Play App Signing. Until then, nothing here is a store build.
