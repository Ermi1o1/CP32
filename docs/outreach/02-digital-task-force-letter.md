**Subject: A working visitor guide for COP32 — technical cooperation and a request to meet the Task Force**

Dear [Name],

We were encouraged by the Task Force's stated commitment to reliable, resilient and secure digital services for COP32. Zega Tech PLC [(registration in progress)] has built a working Android visitor guide for COP32 (a demonstration build with example content, in English, with the structure for Amharic in place), intended for visitors, residents, journalists and remote followers. We have seen the official COP32 website and channels. We offer the guide to the host for adoption, and we would like to cooperate with the Task Force so that our work supports, and never duplicates, the national digital arrangements. If an application is already planned or contracted, we are not a competing bid; what we have is a working reference and a team willing to contribute.

**Why we are writing to the Task Force**
1. **Alignment:** to learn what digital services are planned, so that we integrate with them or avoid overlap.
2. **Connectivity:** the guide works fully offline and installs at about 25 MB. We would like to discuss whether discounted or zero-rated access to official information (including for the platform, if it is recognised) is possible, and what to expect of network performance in the venue area.
3. **Hosting and security:** today the guide stores nothing off the phone and has no account. If services are added later, personal data would be stored in Ethiopia (Proclamation No. 1321/2024). We would like to discuss suitable Ethiopian hosting, security requirements, and any assessment or registration processes the Task Force or INSA expect for applications of this kind.
4. **Data and integration:** we propose simple, open, documented interfaces (for programme and alerts) and can work from spreadsheets. We would like to know whether the Task Force has, or plans, a programme-data service, an alert channel or a host-country application.
5. **Emergency communications:** a pathway for authorised safety alerts to appear in the platform, with signing and dual approval, if the Task Force considers this useful.

**Questions on operations and access (to align with the Task Force's arrangements)**
- Will the Government provide an identity service (single sign-on) for staff accounts, or should the platform operate its own with multi-factor authentication?
- Who should hold the cryptographic keys used to sign official content and alerts, and where should they be hosted?
- Who will liaise with the digital operations team 24/7 during the event for alert authorisation and incidents, and which operations-centre tools should we connect to?
- Which language(s) should the administration interface offer to Government staff, and what training/certification do you expect for staff using it?
- Is a public status page expected?

**What we would like**
- A technical meeting (45 minutes) with the Task Force's focal point.
- Names of the right contacts for hosting/security, data/integration and communications.
- Any technical requirements or standards we should follow.

**What we can share**
A short architecture summary (two data planes: public content on a content-delivery network and personal data in Ethiopian data centres; signed content bundles; offline-first design), our security and privacy approach (OWASP-based verification, independent penetration testing before the pilot and before the event, audit logging, 72-hour incident response), and the application itself, on a phone, with example content. It has not yet had an independent security test; we would want to arrange that with the Task Force's guidance.

We would be glad to adapt to the Task Force's processes.
